# I7 heap occupancy: the missing progress premise and a proposed boundary

Status: feasibility finding and proposed remedy under live I7 commitment5cfedb59, evaluator bebeed31322f96ce9d75044acd71382466fde5c2, pinned Go1.26.7. No runtime setting, evaluator code, host code, public pin or production profile changed. This is not the physical F proof or an unbounded-memory counterexample.

The current source argument does not establish an independent Qmax for an indefinitely reused process. Logical allocation units bound the work of one event, and successful events may be followed by a fresh independent budget. The assigned contract does not bound the number of events between completed collections, nor adopt an allocation-throughput or scheduler-progress bound. Peak reachable application data is not a bound on still-allocated ordinary heap pages. Substituting the GC heap goal for Qmax therefore leaves a real missing implication.

## Concrete path that defeats the present inference

The admitted primitive set contains uppercase. v206/functions.go:829 reserves its bounded primitive cost and calls strings.ToUpper. The output codec also constructs new byte storage (meter_evaluate.go:48 and meter_json_encode.go:127,143). Discarding a result after an evaluation does not call a Go deallocator. meter.go:17-35 explicitly assigns independent budgets to independent events; it introduces no process allocation or collection barrier. These are ordinary supported allocation paths, not an injected provider or a legacy unmetered callback.

Go malloc.go:1112-1117 calls deductAssistCredit while blackening is enabled, and deductAssistCredit:1842-1863 calls gcAssistAlloc when the G is in debt. But mgcmark.go:534-557 returns from that assist while gcCPULimiter.limiting() is true. This return does not refund the debt or refuse the pending allocation. The allocator then continues. The non-preemptible bypass at499-508 is another path requiring accounting, but the ordinary limiter branch alone prevents relying on every event allocation paying enough collection work.

mallocgcSmallNoscan:1412-1417 marks each new object black while the write barrier is enabled; other ordinary allocation variants have the corresponding rule. An object may become unreachable before the event returns and still survive that marking cycle. Sweeping only reclaims objects that the relevant completed marking cycle left unmarked. deductSweepCredit:913-955 paces outstanding sweep work and returns immediately when the sweep ratio is zero; it does not run a new marking cycle for newly unreachable objects. gcTrigger.test:706-710 refuses a new trigger while gcphase is not GCoff. Repeated allocator trigger checks during marking consequently do not turn this into a synchronous completion guarantee.

The limiter bounds a time-accounting ratio, not bytes or event count. mgclimit.go:264-296 enables it when accumulated GC time fills the bucket and disables it on a later update with headroom. Its10ms update period at140 is a threshold tested at update sites, not a10ms allocation cap. findRunnableGCWorker in mgcpacer.go:860-871 performs one such update. Nothing in these paths supplies the number of allocations or new independent event budgets that can run before the missing completion boundary. GOMAXPROCS=1, used by the narrow fixture, does not itself supply that count.

This is a source-supported failure of the proposed implication, not evidence that every selected workload enables the limiter or that a real supported process can grow without bound. I have not proved limiter-state reachability for the closed evaluator workload and have not measured a runaway. A proof that the limiter is unreachable under an exact final host, or a proven allocation-count progress invariant that covers it, could still avoid the remedy below. No wall-clock measurements, GC goal, soft GOMEMLIMIT, MemStats snapshot, available address-space ceiling or successful500-evaluation run substitutes for that proof.

## Smallest concrete remedy to review

Propose a host-owned collection boundary between bounded allocation epochs. For the initial admitted serial profile, one epoch contains the complete bounded preparation/acquisition and evaluation work assigned to it, including success and refusal paths. Before admitting another epoch with fresh allowances, return from the previous event's helper, release its transient references, and call runtime.GC from an ordinary preemptible host frame. The host may carry only the explicitly bounded compiled/program/context/result state that the physical proof counts. It must not retain an unbounded queue of results or inputs across this boundary. Do not place the call inside a provider, codec or evaluator charge operation.

runtime.GC in mgc.go:522-591 waits for an in-progress mark cycle, ensures a following complete cycle, and finishes or waits for its sweep before returning. A blocked collection would block the next epoch rather than permit more evaluator allocation. Thus memory safety would no longer require a fixed wall-clock completion deadline or a fixed number of mutator instructions before ordinary background GC catches up. This says nothing about acceptable latency or availability: runtime.GC may stop the process, and per-epoch cost must be evaluated before production adoption.

One collection is not permission to count all pools as empty. sync/pool.go:257-281 clears old victim caches and moves current caches into the victim generation. Any retained objects there must be covered by a bounded pool-population term or a conservative previous-epoch allowance; unbounded host pooling remains inadmissible. Finalizers, cleanups, other application goroutines, supported runtime helpers and manual spans likewise require their own already-bounded populations. Calling GC alone is not a proof for arbitrary library hosts.

The intended induction has the shape Qmax <= Qfixed + Qretained + Qpool-carry + Qepoch + Qcollector, with each term in globally unavailable8192-byte pages. Qepoch derives from the complete precharged source/evaluator/codec allocation inventory, counting discarded allocations as well as live ones and including allocator rounding and span slack. Qretained covers bounded cross-epoch roots; Qpool-carry covers the explicitly audited generations; Qcollector covers concurrent runtime/helper allocation. The existing P-cache, manual-span and random-padding allowances must be included exactly once. A term depending on Nspan cannot simply be substituted if Nspan already depends on Qmax: any such cycle must be solved or removed. These terms are obligations to establish at an exact candidate, not numbers proved by this note.

This changes a host scheduling/admission premise. It does not change logical W/A/D accounting, introduce GC refunds, decide business results from GC state, change GOGC/GOMEMLIMIT/MemProfileRate, or enable providers. It needs explicit disposition before implementation. If adopted, the smallest coherent delivery should make the boundary non-bypassable for the admitted host path and preserve transaction recovery on process death. Preparation/reload/refusal paths need the same bounded-epoch argument; an Evaluate-only hook would leave repeated compile/rejection allocation outside the proof.

Validation for that candidate should exercise ordering through the real orchestration entry point: no second fresh epoch until collection returns, transient roots released before the call, refusal and cancellation taking the same release path, and bounded result ownership. An omission control that bypasses the boundary should fail that ordering check. Separate pinned-runtime source proof supplies the collection/sweep fact; a fake collector or a few flat RSS samples do not. Keep independent Architecture/Security/Simplification review, exact host/profile identity, and the complete F composition as admission gates.

A fixed-capacity evaluator arena could instead remove the GC dependence, but covering the current Go parser, strings, regex and codecs would be a substantially larger change. Disabling the CPU limiter or assuming a fast scheduler is not proposed. The immediate requested disposition is whether to develop the host-owned boundary as an explicit I7 premise, or keep the original profile and require a missing collector-progress proof. This note does not adopt either option.
