# Review note for Hugh: make verification claims specific

Keep the review workflow unchanged, but make the evidence state which route and distinction each important test actually exercises. For changes involving retries, authority or stored identity, include a small positive/negative pair at the changed boundary. This is a way to make the existing review useful, not another approval step or a requirement for a large new test suite.

The explicit-request-authoring candidate 21341300 illustrates the need. Its reporting artifact451ed431 records broad passing tests and whole-guard omission controls. Independent review nevertheless reproduced two failures through the actual CLI: changing the caller-selected destination under the same key returned the old destination's request, and deleting the accepted branch made an identical retry fail. The existing moved-branch retry control passed. The same code therefore needs both distinctions: changed intent must refuse, while unchanged accepted intent must survive a changed world. Removing the entire retry helper proves neither distinction by itself.

A second evidence issue appears in TestCLIRequestReplaysAnExistingLegacyAct. Both attempts call kernel.Submit directly. That is useful evidence that the original signed event still replays at the kernel boundary; it is not evidence that gs state, MCP state or HTTP act can recognize the old request body after the authoring interface changes. The implementation report's broad statement about legacy retry must say which guarantee has actually been tested. The author has been asked to add the surface case during the existing correction. This note does not claim an independently reproduced third failure.

The same distinction matters in the current Inventory transition. Looking at current compiled handles does not prove the persisted runtime was checked. Each boundary's omission control must reach that boundary without an earlier guard masking its absence. Checking actual SQLite/WAL state is required; filesystem coordination effects must be reported separately from changes to durable projection data. The owned storage child and its current clarification already state those conditions.

A concise review evidence table is enough when useful: claimed behavior, exercised entry point, changed input or world fact, and observed refusal/replay/no-write result. Test names should follow those facts. Keep the normal required CI gates, but do not substitute a suite count, a test's name, a compiling omission mutant or a successful run of a lower layer for the promised user-facing behavior. Run additional checks when the change or a specific uncovered distinction warrants them, rather than repeating the same large suite for reassurance.

These are observations from current work, not measured savings or new members of the closed twenty-delivery sample. It proposes no new lifecycle, general mandatory matrix, source implementation or relaxation of independent exact-head review.
