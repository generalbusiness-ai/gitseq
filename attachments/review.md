# Keep published artifacts when working on another branch

A recovery branch should not make current `main` publications look abandoned. Gitseq currently makes that inference when an artifact is outside the target ancestry and has no unsettled commitment. The merge leaves it live, but the [cleanup rule](cleanup-rule.md) then says its author or a ratifier owes a bare retirement. That turns completed work on another branch into apparent cleanup debt.

I reproduced this with Tailapp's current workroom. Its inbox artifact **#3906**, `7bfc28b1`, was published by sealed merge `7ecffd53` and remains effective, fresh and unretired at the exact local and remote `main` head. The recovery destination is `5d84ac71`. Calling the actual [classifier](classifier.go) for an inbox change on that destination returns **abandoned**, and `PlanSuccession` preserves that classification in its left-live accounting.

The same artifact is an in-target predecessor when the target is `main`. An unrelated changed path excludes it. Adding a synthetic open request that reaches it changes the answer to protected sibling. Those controls locate the problem: publication on another destination does not protect the pointer, while an unfinished task would. We should not need to manufacture promises to keep delivered work visible.

This is a gap in the current rule, rather than a disagreement between code and documentation. I recommend one bounded correction: account for other landed destinations before calling a pointer abandoned or creating retirement debt. Preserve a pointer that still describes another retained destination, using the existing retained/carried accounting if it can express that honestly. Keep genuine abandoned candidates subject to cleanup. The evidence for retention must be explicit and reviewable; a stray branch name or an old ancestor alone is insufficient. Preserve existing signed receipts and avoid adding a new commitment lifecycle.

Acceptance should cover two retained branches, a superseded publication, an actually abandoned candidate and a protected in-flight candidate. Removing the other-destination check must reproduce this mistake. The command, sealed accounting, fold and cleanup guidance must agree; merely changing the UI label would leave the retirement instruction intact. This is a focused design-and-implementation change with medium risk because receipt interpretation is involved.

[Evidence](evidence.json), [reduced classifier input](classifier-input.json) and the [probe](probe_test.go) make the finding inspectable. The full workroom snapshot was tested first; the reduced input retains the relevant reachability and produced an identical result. Both ran against Gitseq `80d4fbf7` in a disposable checkout. The probe supplies the historical upstream fix as a classification input only: it does **not** approve that head for the recovery branch, run a complete merge preflight, or claim that a backport has landed. No artifact was retired and no live service changed. The actual recovery merge still needs its own exact-head review.
