# Review for Hugh: verify against one captured workroom frontier

Recommendation: run the real-record documentation gate against a verified, read-only snapshot prepared once for the validation run. Record the source commit and workroom frontier together. Keep the existing citation checks and failure rules; add no workflow state or approval form.

The publication-fix delivery supplies a concrete failure. At source commit 133cd39c5, the local full race run failed its named-record gate: it had observed depth 19230, while ordinary artifact filing advanced the shared saved checkpoint to 19240. The verifier correctly refused the older observation. The source under test had not changed, but validation now needed investigation and another environment. A separate read-only snapshot at frontier 19241 passed the same real-record documentation suite. Both results were retained in review request #19242. The independent review also passed docset at that source revision. These observations show interference with the live workroom, not a reason to relax rollback protection.

The [gate source](anchor_test.go) opens the checkout's actual workroom and calls Snapshot. In a linked worktree, that uses the repository's shared refs and verification memory. Its purpose is narrower: prove that the documentation's named records exist and have acceptable status at an identified frontier. Live writing during a test adds no evidence for that claim.

The small correction is to make that frontier an explicit test input through the supported attachment path or an equivalent verified snapshot. Use separate refs and read-only configuration, with no actor or sequencer keys. Run the existing named-record and flare checks there, and remove the fixture afterward. A capture failure should remain visible; never reset the live checkpoint, rewind its ref or relabel the original failed run as passing. The later implementation review still examines the actual current workroom and any changes since the captured frontier.

Tailapp's recent pending-queue review provides a useful comparison. Its synthetic disposable backlog reproduced the observed scale, preserved meaningful old-order failure controls, and exercised real control requests without changing the live telemetry queue. The [cross-room evidence summary](evidence.json) names that exact review and its limits. This is a useful working pattern for Gitseq too: use real history or representative data where the condition needs it, while giving a validation run stable inputs and its own mutable state.

Acceptance should demonstrate that concurrent live appends neither corrupt the test's captured view nor change the live checkpoint through the test; missing or unacceptable cited records still fail; and every result names both source head and verified frontier. Keep current review-time checks separate from that captured test claim. I have not measured a projected time saving or counted every historical occurrence.

This recommendation is separate from the already assigned cancellation and whoami timing-test corrections (#19212 and #19245), and from merge-completion preflight (#19206). It is a review recommendation, not an adopted policy or an implementation assignment.
